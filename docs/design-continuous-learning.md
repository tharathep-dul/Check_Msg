# เอกสารออกแบบ — กลไกรับคำสแกมใหม่ต่อเนื่อง และเฝ้าระวังการเสื่อม

สถานะ: **ร่าง รอทบทวน** · 2026-08-11 · อ้างอิง ChekMsg v0.5.0

---

## 1. ปัญหา

เครื่องมือที่ใช้กฎจับได้เฉพาะสิ่งที่มีคนเขียนไว้ คนร้ายเปลี่ยนคำทุกสัปดาห์ แต่โปรเจกต์ยังไม่มีช่องรับข้อมูลกลับเลยสักช่อง

ตัวเลขที่บอกขนาดของปัญหา

```
adversarial   1/12   — และ 7 ใน 12 ไม่พบสัญญาณใดเลย
recall        78.8%  — ณ วันที่ 2026-08-11
```

`78.8%` เป็นค่าของวันนี้ ปีหน้าจะต่ำลงโดยไม่มีใครรู้ เพราะชุดทดสอบยังเป็นชุดเดิม **ความล้มเหลวจะเงียบ** — ตัวเลขพาดหัวยังสวยอยู่ในขณะที่เครื่องมือจับสแกมที่ระบาดจริงไม่ได้แล้ว

## 2. เป้าหมาย

| # | เป้าหมาย | วัดยังไงว่าสำเร็จ |
|---|---|---|
| G1 | รู้ตัวเมื่อความแม่นยำเริ่มเสื่อม | มีกราฟ recall ย้อนหลัง และมี issue เด้งอัตโนมัติเมื่อตก |
| G2 | มีช่องรับคำสแกมใหม่ที่ไม่ต้องรอผู้ใช้ | มีเคสใหม่จากสนามจริงไหลเข้าทุกสัปดาห์ |
| G3 | วัด **pattern lag** ได้ | รู้จำนวนวันจากสแกมระบาดถึงวันที่จับได้ |
| G4 | ไม่ทำลายความน่าเชื่อถือของการวัดผลที่มีอยู่ | ตัวเลขพาดหัวยังมาจากเคสที่คนตรวจแล้วเท่านั้น |

**G4 คือข้อที่ห้ามแลก** ถ้าทำ G1-G3 สำเร็จแต่ตัวเลขเชื่อไม่ได้แล้ว แปลว่าล้มเหลวทั้งหมด

## 3. ข้อจำกัดที่ยอมรับ

- ห้าม auto-merge เข้า `patterns.json` — คนต้องกดอนุมัติทุกครั้ง
- ห้ามให้เคสที่เก็บมาอัตโนมัติเข้าคะแนนก่อนมีคนตรวจ
- ห้ามให้ LLM เป็นแหล่งที่มาของ pattern (สร้างได้แค่เคสทดสอบ)
- ยังไม่แตะข้อมูลผู้ใช้จริงในเฟสนี้ — จึงยังไม่มีภาระ PDPA

## 4. สถาปัตยกรรม

แยกเป็นสองระบบที่ไม่ยุ่งกันเลย เพราะมีระดับความเสี่ยงต่างกันคนละขั้ว

```
┌─────────────── ระบบ A: เฝ้าระวังการเสื่อม ────────────────┐
│  cron รายสัปดาห์                                          │
│  LLM สร้างเคสกัดใหม่ → รันกับ engine → บันทึกคะแนน          │
│  recall ตกต่อเนื่อง → เปิด issue                            │
│  ★ ไม่แตะ patterns.json และ testset.json เลย              │
│  ★ อัตโนมัติ 100% ปลอดภัยเต็มที่                           │
└───────────────────────────────────────────────────────────┘

┌─────────────── ระบบ B: เติมคำ ────────────────────────────┐
│  ประกาศสาธารณะ ─┐                                          │
│  honeypot ──────┼─→ ① เก็บ ────→ tests/inbox/  (กักกัน)   │  อัตโนมัติ
│  ผู้ใช้รายงาน ───┘                    ↓                     │
│                              ② คนติดป้าย scam/legit        │  คน ~30 วิ/เคส
│                                       ↓                     │
│                              ③ เข้า tests/testset.json      │  อัตโนมัติ
│                                 ชุด `field` (นับคะแนน)      │
│                                       ↓                     │
│                              ④ เคสที่แดง → เสนอ pattern     │  เสนออัตโนมัติ
│                                 เปิด PR → CI ตรวจ           │  คนกด merge
└───────────────────────────────────────────────────────────┘
```

**เหตุผลที่แยก** — การ *วัด* ไม่ต้องขออนุญาตใคร จึงอัตโนมัติได้เต็มที่ ส่วนการ *แก้คลังคำ* คือการเปลี่ยนพฤติกรรมเครื่องมือที่คนพึ่งพา จึงต้องมีคนรับผิดชอบ

## 5. กฎ 5 ข้อที่ทำให้ระบบไม่พังตัวเอง

### R1 — เคสมาก่อนคำ

ข้อมูลใหม่ห้ามกลายเป็น pattern โดยตรง ต้องเป็นเคสทดสอบก่อนเสมอ และ **pattern ทุกตัวต้องมีเคสที่แดงรองรับ**

นี่คือกติกาข้อแรกใน `CONTRIBUTING.md` ที่มีอยู่แล้ว เพียงแต่บังคับใช้กับท่ออัตโนมัติด้วย ผลคือชุดทดสอบโตเร็วกว่าคลังคำเสมอ — กัน overfit เชิงโครงสร้าง ไม่ต้องพึ่งวินัยคน

### R2 — ของใหม่เข้าชุดกักกัน ยังไม่นับคะแนน

เคสที่เก็บมาอัตโนมัติอยู่ใน `tests/inbox/` ซึ่งไม่ถูกโหลดเข้าการคิดคะแนน จนกว่าคนจะติดป้ายและย้ายเข้า `testset.json`

ถ้าปล่อยให้ไหลเข้าคะแนนเลย ตัวเลขพาดหัวจะเน่าเงียบ ๆ — บาปเดียวกับ 86% ในรายงานปี 2025 เป๊ะ

### R3 — คนออกข้อสอบห้ามเห็นเฉลย

LLM ที่สร้างเคสกัด **ต้องไม่เห็น `patterns.json`** ถ้าเห็น มันจะเขียนเคสที่วนอยู่รอบคำที่มีอยู่แล้ว = กลับไปเป็นกับดัก `regression_v03` แค่เปลี่ยนคนออกข้อสอบเป็น AI

ป้อนให้มันแค่ตัวอย่างสแกมจริง แล้วสั่งให้เขียนใหม่ในความหมายเดียวกันด้วยคำคนละชุด

### R4 — LLM สร้างได้แค่เคสทดสอบ ห้ามสร้าง pattern

pattern มาจากข้อความจริงเท่านั้น ไม่งั้นเครื่องมือเรียนรู้จากตัวเอง

### R5 — แยกความน่าเชื่อของแหล่ง

| แหล่ง | เชื่อได้ | ปฏิบัติ |
|---|---|---|
| ประกาศทางการ | สูง | ติดป้าย `scam` ล่วงหน้าได้ คนยืนยันเร็ว |
| honeypot (เบอร์ตัวเอง) | สูง | ทุกอย่างที่เข้ามาคือไม่พึงประสงค์ |
| ผู้ใช้รายงาน | **ต่ำ** | คนต้องดูทุกเคส — **ช่องที่คนร้ายจะใช้โจมตี** |
| LLM | ไม่เกี่ยว | เคสทดสอบเท่านั้น |

**ภัยที่ R5 ป้องกัน** — ส่งรายงานปลอมที่ระบุว่า `"ยอดเงินเข้าบัญชี"` เป็นสแกม ถ้าคำนั้นเข้าคลังได้ ข้อความธนาคารจริงทุกฉบับจะกลายเป็นสแกม และผู้ใช้เลิกเชื่อเครื่องมือทันที

## 6. ระบบ A — เฝ้าระวังการเสื่อม

### ไฟล์ที่เพิ่ม

```
tools/watch-decay.mjs                 สคริปต์หลัก
tests/fixtures/scam-seeds.json        ตัวอย่างสแกมจริงสำหรับป้อน LLM
tests/history/decay.jsonl             บันทึกคะแนนย้อนหลัง
.github/workflows/decay-watch.yml     cron รายสัปดาห์
```

### กลไก

1. อ่าน `scam-seeds.json` — ข้อความสแกมจริงที่ติดป้ายแล้ว พร้อมวันที่พบครั้งแรก
2. ส่งให้ LLM สร้างเคสใหม่ **โดยไม่ส่ง `patterns.json` ไปด้วย** (R3)
3. รันเคสที่ได้กับ engine ปัจจุบัน
4. **รันชุดทดสอบคงที่ 56 เคสด้วย เป็นตัวควบคุม**
5. บันทึกลง `decay.jsonl` หนึ่งบรรทัดต่อรอบ
6. ประเมินแนวโน้มจากค่าเฉลี่ยเคลื่อนที่ 4 สัปดาห์ — ตกเกินเกณฑ์ติดกัน 2 รอบ จึงเปิด issue

### ทำไมต้องมีตัวควบคุม (ข้อ 4)

เคสที่ LLM สร้างต่างกันทุกสัปดาห์ คะแนนจึงมี noise ตามธรรมชาติ ชุดคงที่ 56 เคสคือตัวแยกแยะ

| ชุดคงที่ | เคสที่สร้างใหม่ | แปลว่า |
|---|---|---|
| นิ่ง | ตก | **การเสื่อมจริง** — คนร้ายใช้คำที่ระบบไม่รู้จัก |
| ตก | ตก | มีคนแก้ engine หรือ pattern พัง — ดู commit ล่าสุด |
| นิ่ง | นิ่ง | ปกติ |

### รูปแบบ `decay.jsonl`

```json
{"date":"2026-08-11","patternsVersion":"0.5.0","seedsVersion":"1.0.0",
 "generated":{"n":50,"caught":21,"recall":0.42},
 "control":{"n":56,"correct":44,"recall":0.788},
 "model":"claude-opus-5"}
```

### วัด pattern lag

`scam-seeds.json` แต่ละรายการเก็บ `firstSeen` (วันที่ประกาศเตือนออก) เมื่อ engine จับเคสนั้นได้ครั้งแรก บันทึก `caughtAt`

```
pattern lag = caughtAt − firstSeen
```

- ต่ำกว่า 7 วัน = ตามคนร้ายทัน
- เกิน 30 วัน = ตายแล้วแต่ตัวเลข accuracy ยังสวยอยู่

### สิ่งที่ระบบ A ไม่ทำ

ไม่แตะ `patterns.json` ไม่แตะ `testset.json` ไม่เปิด PR — **เขียนได้แค่ `decay.jsonl` กับ GitHub issue เท่านั้น**

เคสที่ LLM สร้างจะไม่ถูกเก็บถาวรเข้าชุดทดสอบ เพราะถ้าเก็บ มันจะกลายเป็นข้อสอบที่ค่อย ๆ ถูก overfit

## 7. ระบบ B — เติมคำ

### ไฟล์ที่เพิ่ม

```
tools/harvest-advisories.mjs      ดึงประกาศ → tests/inbox/
tools/review-inbox.mjs            CLI ให้คนติดป้าย
tools/propose-patterns.mjs        เคสแดง → เสนอ pattern → เปิด PR
tests/inbox/YYYY-Www.json         ชุดกักกันรายสัปดาห์
```

### ① เก็บ — รูปแบบ `tests/inbox/`

```json
{
  "harvested": "2026-08-11",
  "source": { "type": "advisory", "name": "ตร.ไซเบอร์", "url": "https://...", "publishedAt": "2026-08-05" },
  "items": [
    { "id": "inb_2026w33_001",
      "text": "พัสดุตกค้าง กรุณาชำระค่าภาษี 45 บ. ที่ลิงค์นี้",
      "label": null,
      "engineVerdict": "unsure",
      "engineScore": "s0/l0" }
  ]
}
```

`engineVerdict` บันทึกตั้งแต่ตอนเก็บ ทำให้รู้ทันทีว่าเคสไหนคือช่องว่างจริงโดยยังไม่ต้องมีคนดู

### ② คนติดป้าย

```bash
npm run review
```

แสดงทีละเคส: ข้อความ, ที่มา, ผลที่ engine ตอบ แล้วรับคีย์เดียว

```
[s] สแกม   [l] ปกติ   [u] กำกวม   [x] ทิ้ง   [q] ออก
```

เป้าหมายคือ **ไม่เกิน 30 วินาทีต่อเคส** ถ้าช้ากว่านี้จะไม่มีใครทำต่อเนื่อง

### ③ เข้าชุดทดสอบ

เคสที่ติดป้ายแล้วย้ายเข้าชุดใหม่ใน `testset.json` ชื่อ **`field`** — เคสจากสนามจริง **นับคะแนน** เพราะผ่านคนแล้ว

```json
"field": {
  "label": "ข้อความจริงจากสนาม — เก็บอัตโนมัติ ติดป้ายโดยคน",
  "cases": [
    { "id": "f001", "lang": "th", "expect": "scam", "text": "...",
      "note": "ตร.ไซเบอร์ 2026-08-05", "firstSeen": "2026-08-05" }
  ]
}
```

### ④ เสนอ pattern

เฉพาะเคสที่ `expect: scam` แต่ engine ตอบ `unsure`/`legit` เท่านั้น (R1)

LLM เสนอคำ candidate → สคริปต์ทดลองใส่ → รันชุดทดสอบเต็ม → **ตัดคำที่ทำให้เคสเดิมพังทิ้งอัตโนมัติ** → เปิด PR เฉพาะคำที่รอด

รูปแบบ pattern ที่เพิ่ม — ปิดช่องว่าง provenance ที่พบตอนสำรวจ (ปัจจุบัน 0 จาก 164 คำบันทึกที่มาไว้)

```json
{ "id": "s_th_import_tax", "lang": "th", "cat": "delivery",
  "match": "ค่าภาษีนำเข้า", "w": 4,
  "src": "advisory:ตร.ไซเบอร์ 2026-08-05",
  "added": "2026-08-11",
  "case": "field/f001" }
```

## 8. สิ่งที่ CI ต้องตรวจเพิ่ม

ต่อยอดจาก 4 ข้อที่มีอยู่

| # | ตรวจอะไร | ทำไม |
|---|---|---|
| 5 | pattern ที่ `added` หลัง 2026-08-11 ต้องมีครบ `src`, `added`, `case` | ของเก่า 164 คำ grandfather ไว้ ไม่ย้อนไปแก้ |
| 6 | ทุกค่า `case` ที่อ้าง ต้องมีอยู่จริงใน `testset.json` | ทำให้ **R1 บังคับใช้ได้** ไม่ใช่แค่คำแนะนำ |
| 7 | `tests/inbox/` ต้องไม่มีเคส `label: null` ค้างเกิน 30 วัน | เตือนเฉย ๆ ไม่ fail — กันของกองจนไม่มีใครดู |

**ข้อ 6 คือหัวใจ** — ถ้าไม่มี กฎ R1 จะเป็นแค่ความตั้งใจดีที่ค่อย ๆ ถูกละเลย

## 9. ความปลอดภัยของท่อ

- ทั้งสองระบบทำงานใน **GitHub Actions** ไม่ใช่บน production server
- LLM API key อยู่ใน GitHub Secrets ไม่แตะเครื่องที่ให้บริการผู้ใช้
- PR อัตโนมัติมาจาก branch `auto/patterns-YYYY-MM-DD` และ **ไม่มีสิทธิ์ merge ตัวเอง**
- ต้องตั้ง **branch protection** บน `main`: ต้องผ่าน CI และต้องมีคน approve
- `harvest` อ่านอย่างเดียว ไม่ส่งข้อมูลอะไรออกนอกจากคำขอไปยัง LLM

## 10. สิ่งที่จะทำในเฟสนี้ และสิ่งที่ยังไม่ทำ

### ทำ

| ลำดับ | ทำอะไร | แรง | ได้อะไร |
|---|---|---|---|
| 1 | ระบบ A ทั้งหมด | ~1 วัน | G1, G3 — รู้ตัวเมื่อเสื่อม |
| 2 | ระบบ B เฉพาะแหล่ง "ประกาศสาธารณะ" | ~1-2 วัน | G2 — ช่องรับคำใหม่ช่องแรก |
| 3 | CI ข้อ 5-7 | ~2 ชม. | G4 — บังคับใช้ R1 |

ทั้งสามข้อ **ไม่ต้องมีผู้ใช้ ไม่ต้องมีซิม ไม่แตะข้อมูลส่วนบุคคล** จึงเริ่มได้ทันทีโดยไม่ต้องรออะไร

### ยังไม่ทำ

| ไม่ทำ | เพราะ |
|---|---|
| honeypot | ต้องมีซิมและท่อรับ SMS — เสียบเข้าท่อเดิมทีหลังได้ |
| ปุ่มรายงานผลผิด | เป็นโปรเจกต์แยก มีเรื่อง PDPA และการขอความยินยอมต้องออกแบบ |
| dashboard | `decay.jsonl` + GitHub issue เพียงพอแล้วในเฟสนี้ |
| auto-merge | ขัดข้อจำกัดที่ตกลงกันไว้ |
| ชั้น LLM ตอนใช้งานจริง | คนละเรื่องกับเอกสารนี้ |

## 11. ความเสี่ยงที่เหลืออยู่

| ความเสี่ยง | ผลกระทบ | รับมือ |
|---|---|---|
| ไม่มีใครติดป้ายเคสใน inbox | ท่อตัน G2 ล้มเหลว | CI ข้อ 7 เตือน + ออกแบบ CLI ให้เร็วกว่า 30 วิ/เคส |
| LLM สร้างเคสคุณภาพต่ำ | ตัวเลขเฝ้าระวังมั่ว | มีชุดควบคุม 56 เคสคอยแยกแยะ |

## 12. คำถามที่ยังไม่ได้ตอบ

1. **จะดึงประกาศจากที่ไหนบ้าง** — ต้องสำรวจว่าแหล่งไหนมีข้อความสแกมจริงให้ดึงได้ และมี RSS/API หรือต้อง scrape
2. **ใครเป็นคนติดป้าย** — ตอนนี้คือเจ้าของโปรเจกต์ ถ้าจะขยายต้องคิดเรื่องสิทธิ์
3. **เกณฑ์เปิด issue ที่เหมาะสม** — ต้องเก็บข้อมูล 4-6 สัปดาห์ก่อนถึงจะตั้งค่าได้อย่างมีเหตุผล เฟสแรกให้บันทึกอย่างเดียวไม่ต้องเตือน
