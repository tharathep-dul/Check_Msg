# ChekMsg — คู่มือใช้งานและทดสอบ

เอกสารนี้ตอบคำถาม 3 ข้อ: ใช้ยังไง, ทดสอบยังไง, และแก้อะไรได้บ้างโดยไม่ต้องแตะโค้ด

เวอร์ชันปัจจุบัน **v0.5.0** · อัปเดต 2026-08-11

---

## 1. ใช้งาน

### เร็วที่สุด — ไม่ต้องติดตั้งอะไร

double-click ไฟล์ `dist/chekmsg-standalone.html` เปิดได้ทันที ใช้ออฟไลน์ได้ ส่งต่อทาง LINE หรืออีเมลให้คนอื่นลองได้เลย เพราะรวม engine กับ pattern ไว้ในไฟล์เดียว

เหมาะกับ: สาธิตหน้าห้อง, ให้ญาติลองใช้, แนบไปกับรายงาน

### รันในเครื่องแบบพัฒนา

`index.html` โหลด `patterns.json` ผ่าน `fetch` จึงต้องเปิดผ่าน web server (double-click จะติด CORS ของ `file://`)

```bash
python3 -m http.server 8080
# เปิด http://localhost:8080
```

### ขึ้น server จริง

เป็น static site ล้วน คัดลอกทั้งโฟลเดอร์ไปวางได้เลย ไม่ต้อง build ไม่มี environment variable ไม่มี runtime

```bash
rsync -av ./ user@server:/var/www/chekmsg/
```

หรือใช้ Cloudflare Pages / Netlify / GitHub Pages / S3 ก็ได้

### 3 วิธีป้อนข้อความ

| วิธี | ทำยังไง |
|---|---|
| พิมพ์หรือวางข้อความ | วางลงช่องกรอกแล้วกดตรวจสอบ |
| ลากภาพมาวาง | ลาก screenshot ลงกรอบเส้นประ |
| วางภาพจากคลิปบอร์ด | กด `Ctrl+V` (หรือ `Cmd+V`) ตอนที่ copy ภาพไว้ |

ภาพจะถูกแปลงเป็นข้อความแล้ว **ใส่ในช่องกรอกให้ตรวจทานก่อน** ไม่ตรวจอัตโนมัติทันที เพราะ OCR ภาษาไทยยังเพี้ยนได้

### อ่านผลลัพธ์

| ผล | ความหมาย |
|---|---|
| ⚠ น่าจะเป็นสแกม | คะแนนฝั่งสแกมนำฝั่งปกติตั้งแต่ 4 ขึ้นไป |
| ✓ น่าจะเป็นข้อความปกติ | คะแนนฝั่งปกตินำตั้งแต่ 2 ขึ้นไป |
| ? ยืนยันไม่ได้ | ไม่ถึงเกณฑ์ทั้งสองทาง |

**"น่าจะเป็นข้อความปกติ" แปลว่า "ไม่พบสัญญาณอันตราย" ไม่ได้แปลว่า "ปลอดภัย"** ระบบจับได้เฉพาะคำที่มีคนใส่ไว้ใน `patterns.json` แล้วเท่านั้น สแกมที่ใช้คำใหม่จะได้ผลว่า "ยืนยันไม่ได้"

## 2. ทดสอบ

### คำสั่งที่ใช้บ่อย

```bash
npm test                                   # พิมพ์ผลออกหน้าจอ
npm run test:report                        # เขียน tests/last-report.md
node tests/run-tests.js --set adversarial  # รันเฉพาะชุดเดียว
```

`npm test` คืน **exit code 1** เมื่อเจอสแกมที่ถูกตอบว่าเป็นข้อความปกติ CI จึงแดงทันทีในกรณีนั้น

### ชุดทดสอบมี 7 ชุด แต่ละชุดตอบคำถามคนละข้อ

| ชุด | จำนวน | ถามว่าอะไร | อ้างเป็นความแม่นยำได้ไหม |
|---|---:|---|---|
| `regression_v03` | 15 | แก้แล้วของเดิมพังไหม | **ไม่ได้** — เขียนจาก keyword ของตัวเอง |
| `holdout_bank_real` | 15 | ข้อความธนาคารจริงถูกตีว่าสแกมไหม | ได้ |
| `holdout_scam_th` | 12 | จับสแกมไทยที่ระบาดจริงได้ไหม | ได้ |
| `holdout_scam_en` | 6 | จับสแกมภาษาอังกฤษได้ไหม | ได้ |
| `holdout_ambiguous` | 4 | เครื่องมือมั่วเดาหรือเปล่า | ได้ |
| `evasion` | 7 | ตรรกะถูกหลอกด้วยเทคนิคหลบได้ไหม | ได้ — **ต้องผ่านทุกข้อ** |
| `adversarial` | 12 | เปราะแค่ไหนเมื่อคนร้ายเลี่ยงคำ | ได้ — **ตัวเลขที่สำคัญที่สุด** |

รวม 71 เคส แต่คิดคะแนนจาก **56 เคส** เพราะตัด `regression_v03` ออก

### ความต่างระหว่าง `evasion` กับ `adversarial` — สำคัญมาก

ทั้งสองชุดเป็นข้อความที่จงใจหลบ แต่คนละชนิดของปัญหา และแก้คนละวิธี

| | `evasion` | `adversarial` |
|---|---|---|
| ปัญหาคือ | บั๊กของตรรกะใน `engine.js` | คำที่ยังไม่มีในคลัง |
| คำที่ใช้ | มีอยู่ในคลังแล้ว | ไม่มีในคลัง |
| ต้องผ่านไหม | **ทุกข้อ** | ไม่ — ใช้ดูแนวโน้ม |
| แก้ยังไง | แก้ `engine.js` | **ห้ามไล่แก้ทีละข้อ** |

ตัวอย่าง `evasion` — ข้อความนี้ใช้คำที่อยู่ในคลังครบทุกคำ แต่ v0.4 ตอบว่า `legit`

```
ธนาคารไม่เคยขอ บัญชีของท่านจะถูกระงับ ธนาคารไม่เคยขอ กรุณากดลิงก์
ยืนยันตัวตน ธนาคารไม่เคยขอ แจ้งรหัส OTP ด่วน
```

คนร้ายแทรกคำปฏิเสธคั่นทุกวลี ระบบเดิมจึงล้างสัญญาณสแกมทิ้งหมดแล้วแถมคะแนนฝั่งปกติให้ด้วย v0.5 แก้แล้ว ข้อความนี้ได้ `scam s15/l0`

ส่วน `adversarial` ได้ 1/12 ซึ่ง**ถูกต้องแล้ว** ถ้าชุดนี้ได้คะแนนสูงแปลว่าเขียนไม่พอกัด หรือแย่กว่านั้นคือมีคนไล่เพิ่ม pattern ให้ผ่านทีละข้อ ซึ่งคือการจำข้อสอบ

### การให้คะแนนแยก 3 ระดับ

ความผิดพลาดไม่เท่ากัน จึงนับแยก

| ระดับ | หมายถึง | อันตรายแค่ไหน |
|---|---|---|
| `correct` | ตอบตรง | — |
| `soft miss` | ควรตอบชัดแต่ตอบ `unsure` | ปลอดภัย แต่ไม่ช่วยตัดสินใจ |
| `hard miss` | ตอบผิดข้าง | **สแกมที่ถูกตอบว่าปกติ = คนเสียเงินจริง** |

### ตัวเลขปัจจุบัน

```
precision 100.0%   ตอบว่าสแกม แล้วเป็นสแกมจริงทุกครั้ง
recall     78.8%   สแกมทั้งหมด จับได้ 78.8%
F1         88.1%
hard miss      0
soft miss  12/56   (21.4%)
```

### เพิ่มเคสทดสอบเมื่อไร

**ทุกครั้งที่เจอข้อความที่ระบบตอบผิด ให้เพิ่มลง `tests/testset.json` ก่อน แล้วค่อยแก้ให้ผ่าน** วิธีนี้ทำให้เคสนั้นไม่ย้อนกลับมาพังอีก

```json
{ "id": "s13", "lang": "th", "expect": "scam", "text": "...", "note": "เจอจากไหน" }
```

### CI

`.github/workflows/ci.yml` รันทุก push และทุก PR บน Node 20 และ 22 ตรวจ 4 อย่าง

1. `npm test` ไม่มี hard miss
2. `node build.js` ผ่าน
3. `dist/` ตรงกับ `index.html` + `patterns.json` ปัจจุบัน — ลืม build แล้ว commit จะแดง
4. ไม่มี `.env` ถูก track และไม่มีอะไรที่หน้าตาเหมือน API key ในซอร์ส

## 3. เพิ่มหรือแก้คำ โดยไม่ต้องแตะโค้ด

### วิธีที่ง่ายที่สุด — หน้า admin

```bash
python3 -m http.server 8080
# เปิด http://localhost:8080/admin.html
```

หน้านี้ทำ 4 อย่างในที่เดียว

| ส่วน | ทำอะไรได้ |
|---|---|
| ทดสอบข้อความ | วางข้อความจริง ดูสัญญาณที่จับได้และคะแนนแต่ละตัว |
| ผลชุดทดสอบ | รันใหม่อัตโนมัติทุกครั้งที่แก้ เทียบกับตอนเปิดหน้า |
| คลังคำ | ค้นหา กรอง แก้คำ แก้น้ำหนัก เปลี่ยนหมวด ลบ เพิ่ม |
| ดาวน์โหลด | `patterns.json` ตัวใหม่ และรายงานผลทดสอบ `.md` |

**หัวใจคือช่องเทียบผลก่อน-หลัง** เพิ่มคำแล้วมันบอกทันทีว่าเคสไหนดีขึ้น เคสไหนพังลง เช่นถ้าใส่คำว่า "ชำระ" น้ำหนัก 5 มันจะเตือนว่าข้อความจริง "ชำระเงินเรียบร้อย ค่าน้ำประปา 285 บาท" ที่เคยตอบถูกกลับตอบผิดแล้ว

หน้านี้ไม่บันทึกอะไรลง server — แก้ในหน่วยความจำเบราว์เซอร์ล้วน **ปิดแท็บโดยไม่ดาวน์โหลด = การแก้หายหมด**

### แก้ไฟล์ตรง ๆ

```json
{ "id": "s_th_new", "lang": "th", "cat": "delivery", "match": "ค่าภาษีนำเข้า", "w": 4 }
```

| ฟิลด์ | ความหมาย |
|---|---|
| `id` | ต้องไม่ซ้ำ |
| `lang` | `th` หรือ `en` — มีผลกับความยาวหน้าต่างตรวจคำปฏิเสธ |
| `cat` | หมวด ต้องมีใน `categories` — **หมวดเดียวกันนับสูงสุดครั้งเดียว** |
| `match` | ข้อความที่จะค้นหา (ไม่สนตัวพิมพ์ ทนการแทรกช่องว่างและอักขระล่องหน) |
| `w` | น้ำหนัก 1–5 |

**ตั้งน้ำหนักยังไง**

| w | ใช้เมื่อ | ตัวอย่าง |
|---|---|---|
| 1 | พบในข้อความปกติได้บ่อย | `ด่วน`, `urgent` |
| 2–3 | บ่งชี้ได้แต่ไม่เด็ดขาด | `กดลิงก์`, `พาร์ทไทม์` |
| 4–5 | แทบไม่พบในข้อความจริง | `ไม่เช็คบูโร`, `send your otp` |

คำที่กว้างเกินไปต้องได้น้ำหนักต่ำ หรือเขียนให้ยาวขึ้นจนเฉพาะเจาะจง

**แก้เสร็จต้องรัน `npm test` ทุกครั้ง** ถ้า hard miss เพิ่มขึ้น แปลว่าคำที่เพิ่งใส่ทำของเดิมพัง

### ค่าที่ปรับได้อื่น ๆ ใน `patterns.json`

| คีย์ | ทำอะไร |
|---|---|
| `thresholds.scamMargin` | ส่วนต่างคะแนนที่ทำให้ตัดสินว่าสแกม (ปัจจุบัน 4) |
| `thresholds.legitMargin` | ส่วนต่างที่ทำให้ตัดสินว่าปกติ (ปัจจุบัน 2) |
| `negatableCats` | หมวดที่คำปฏิเสธมีผล — ธนาคารไม่เคยเขียนว่า "เราจะไม่ระงับบัญชีคุณ" |
| `negationGuard.threshold` | เจอคำปฏิเสธแยกกันกี่กลุ่มถือว่าจงใจยัด (ปัจจุบัน 3) |
| `linkCheck.trustedDomains` | โดเมนจริงของธนาคาร/หน่วยงานรัฐ |
| `linkCheck.tldAllow` | TLD ที่เชื่อว่าเป็นลิงก์จริงเมื่อไม่มี `http://` หรือ path |

## 4. OCR — อ่านข้อความจากภาพ

มี 2 โหมด สลับด้วยตัวแปรเดียวใน `index.html`

| โหมด | ตั้งค่า | ภาษาไทย | ภาพออกจากเครื่อง |
|---|---|---|---|
| Tesseract | ปล่อย `OCR.proxyUrl` ว่าง | เพี้ยนมาก | ไม่ออก |
| Typhoon | ใส่ URL ของ `ocr-proxy/` | แม่น | ออก |

**ค่าเริ่มต้นคือ Tesseract** ข้อมูลจึงไม่ออกจากเครื่องเลย

ถ้าเปิดโหมด Typhoon ข้อความ privacy ในหน้าเว็บจะเปลี่ยนเองอัตโนมัติเพื่อบอกผู้ใช้ว่าภาพถูกส่งออกไป — **อย่าแก้ให้มันคงที่** เพราะภาพ SMS ธนาคารเป็นข้อมูลส่วนบุคคล

> ตั้ง `proxyUrl` เป็นโดเมนอื่นแล้วต้องเติมโดเมนนั้นใน `connect-src` ของ CSP ใน `index.html` ด้วย ไม่งั้นเบราว์เซอร์จะบล็อกเงียบ ๆ

## 5. ก่อน commit ทุกครั้ง

```bash
npm test                      # ต้องไม่มี hard miss
node build.js                 # ต้อง build ผ่าน
git diff --exit-code dist/    # dist ต้องตรงกับ source
```

**ห้ามเด็ดขาด**

- commit `.env` หรือ API key
- ใส่ API key ในไฟล์ฝั่ง client — key ต้องอยู่ใน `ocr-proxy` เท่านั้น
- ลบข้อความเตือนผู้ใช้ในหน้าเว็บ ทั้งส่วน "เครื่องมือนี้ตัดสินอย่างไร" และข้อความเรื่องการส่งภาพ
- เขียนข้อความ privacy แบบตายตัว — ต้องสลับตาม `OCR.proxyUrl`
- เปลี่ยน `OCR.cdn` โดยไม่คำนวณ `cdnIntegrity` ใหม่
